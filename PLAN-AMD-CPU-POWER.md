# AMD CPU package power in htop-gpu

Implemented on 2026-11-19 in the development source based on htop commit `1c205705`. The working-tree meter passed simulated AMD and live Intel tests. AMD hardware validation is pending. The installed package is 3.5.3-18. See [AUDIT.md](AUDIT.md) for results.

## Which AMD systems can supply watts?

Start with Linux powercap. The in-tree RAPL MSR driver lists AMD CPU families 17h, 19h and 1Ah. It registers the control type `intel-rapl` even on AMD and maps package energy on these CPUs. Its AMD register table supplies no long-term package power limit. Discover the actual readable package zone at runtime. CPU family membership alone cannot confirm that a kernel, firmware or virtual machine exposes usable counters. [Linux driver](https://github.com/torvalds/linux/blob/master/drivers/powercap/intel_rapl_msr.c) · [Powercap interface](https://docs.kernel.org/power/powercap/powercap.html)

## How MangoHud reads AMD RAPL

Reviewed the v0.8.4 release and upstream commit `199227b1` (2026-11-15). Both use the same RAPL initializer and watt calculation. The older revision previously cited in this plan gated discovery on Intel coretemp. That gate is absent from both versions examined here. [Release source](https://github.com/flightlessmango/MangoHud/blob/v0.8.4/src/cpu.cpp) · [Pinned upstream source](https://github.com/flightlessmango/MangoHud/blob/199227b197455f8099d5ffef688bfee875e62efc/src/cpu.cpp#L879-L955)

1. **Selecting a source.** v0.8.4 probes hwmon drivers such as k10temp, zenpower and zenergy, then checks whether an AMD APU supplies a positive CPU power reading. If neither provides a source, it scans `/sys/class/powercap/`. The upstream revision also checks a Deckard-specific source before powercap. The first entry whose `name` is exactly `package-0` is tried. Opening its `energy_uj` for reading is sufficient. A GPU, a companion hwmon driver and a PL1 file are all optional for the RAPL path. One Zen 5 tester confirmed that falling through to RAPL recovered readings when APU metrics gave zero. [Backend selection](https://github.com/flightlessmango/MangoHud/blob/v0.8.4/src/cpu.cpp#L732-L800) · [Hardware report and confirmed fix](https://github.com/flightlessmango/MangoHud/issues/1874)
2. **Converting energy to watts.** The reader keeps the file open, rereads the cumulative microjoules, and timestamps each successful read. When the previous counter was positive and the new value is larger, it divides the energy increase by elapsed microseconds. One µJ/µs equals one watt. Both operands are integers, so 10,625,000 µJ over 250,000 µs becomes 42 W even though the interval average is 42.5 W. HUD formatting can then display that value as `42.0 W`. The calculation uses only package 0. [RAPL reader](https://github.com/flightlessmango/MangoHud/blob/199227b197455f8099d5ffef688bfee875e62efc/src/cpu.cpp#L460-L485) · [HUD formatting](https://github.com/flightlessmango/MangoHud/blob/v0.8.4/src/hud_elements.cpp)
3. **First sample, wrap and failure.** The update starts with a local power value of zero. On the first successful read, an unchanged counter, or a counter decrease, MangoHud publishes zero and saves a fresh baseline. It does not consult the wrap range. An open failure rejects the RAPL source. Discovery can run up to five times. Once selected, a parse/read failure returns before updating the stored watt value, so the overlay can retain an earlier reading. [Initializer, reader and update](https://github.com/flightlessmango/MangoHud/blob/199227b197455f8099d5ffef688bfee875e62efc/src/cpu.cpp) · [Overlay sampling](https://github.com/flightlessmango/MangoHud/blob/v0.8.4/src/overlay.cpp)

For htop-gpu, use the kernel's readable package counters directly. The existing sampler already computes fractional watts across discovered packages and handles counter wrap using the exported range. Keep the explicit `no access` and `N/A` states, and let a missing PL1 suppress only the limit. Acceptance tests should include the 42.5 W interval above with no constraint files and a two-socket case where package 1 contributes measurable power. A future AMD comparison with MangoHud should record the selected backend, compare the same socket over comparable time windows, and allow for MangoHud's integer truncation. Consider zenergy separately if a hardware report establishes the need for a package-labelled alternative.

## Implementation order

1. **Reuse the package sampler.** In `src/htop/linux/IntelRAPL.c`, the change in microjoules divided by elapsed seconds and one million already gives average watts. Existing tests cover valid watts with an unavailable limit. Keep package energy and the optional limit independent through the display path. Count each top-level package once and exclude core subzones and MMIO duplicates. Only present a combined limit when every included package supplies a valid positive limit. A failed energy read for one discovered socket must invalidate the combined watts for that interval.
2. **Make the limit optional in the meter.** In `src/htop/linux/IntelRAPLMeter.c`, evaluate sample status and watts first. Use the limit only for the denominator and the limit label. Keep the saved meter ID `IntelCPUPower` and the existing `Pwr` caption. Use “CPU package power” in F2 Setup and explain that a reported long-term limit enables percentage scaling. The adjacent CPU heading already reads the model from cpuinfo. Give its Setup entry a vendor-neutral label and retain its `IntelCPUInfo` ID.
3. **Handle all four display modes.** With a usable limit, keep the current Intel presentation and check it in every mode. With watts alone, show a value such as `42.0W` in text and LED modes. In bar mode show the watts without a filled percentage bar. In graph mode use a numeric watts fallback in the existing graph area. Preserve the user's selected mode and layout height, and resume the percentage chart when a limit returns. Discard obsolete percentage history across switches. The meter class currently declares a fixed percentage chart. Check the actual bar and graph draw paths in `src/htop/Meter.c` and keep fallback rendering local to the CPU meter where possible. Setting the denominator to zero alone does not implement this behavior.
4. **Keep failure states meaningful.** The initial sample establishes a baseline. Show `N/A` until a valid interval exists, including after energy counters disappear and return. Show `no access` on energy permission errors. A readable counter that stays constant across a valid interval yields a real `0.0W`. An absent, invalid or unreadable limit only removes the limit display. Use the kernel's counter range for wraparound. If the range is unavailable when the counter decreases, discard that interval and establish a fresh baseline.

## Verification without an AMD CPU

Extend `tools/test-rapl.py` and run the full htop executable against the same fake sysfs using a throwaway config. Test the user-visible output as well as the sampler. Existing sampler checks can pass while the meter still prints `N/A`.

| Scenario | Expected result |
| --- | --- |
| AMD-shaped package with no constraint files, energy increasing from 1,000,000 to 43,000,000 µJ over one second | First sample unavailable, second sample 42.0 W. All four modes follow the watts-only display rules. |
| Two package zones present at startup, increasing by 10 J and 20 J over one second, plus core and MMIO duplicates | Total 30.0 W. A limit on only one socket supplies no combined denominator. |
| Fixed watts while a valid PL1 disappears, becomes zero or malformed, then returns with a different value | Same running process keeps reporting watts. Bar and graph switch cleanly in both directions. Intel with a valid limit shows the reported denominator. |
| Counter wrap, missing wrap range, permission loss and recovery, zone removal, unchanged energy | Check the exact wrapped delta, unavailable interval, permission message, fresh baseline and genuine zero respectively. |
| Existing config with the historical meter IDs and an AMD model string in fake cpuinfo | Both meters load, the heading shows the AMD model, and Setup offers each entry once. |

Use deterministic timestamps and sanitizer builds. Keep the Intel live check on the 270K Plus, including its known PL1. Make the live portion of the harness suitable for other hosts by checking PL1 against sysfs when available and reporting unavailable hardware or permissions explicitly. Keep the deterministic tests runnable independently. Run the normal build, style check, sampler, RAPL and heading suites. Capture full-meter output in a narrow layout as well as at normal width. As a negative control, verify that the watts-only display test fails with the released meter.

## Evidence to record before advertising coverage

Record fixture results and the live Intel regression in `AUDIT.md`. In the README describe AMD support in terms of readable package counters and label the initial coverage as simulated. The sampler currently tracks up to eight packages and can miss a package that appears after initial discovery (deferred audit finding 7). Limit multi-socket claims to what was exercised.

When a Ryzen or EPYC tester is available, collect the CPU model, kernel, package-zone names, counter ranges and permission state. Compare displayed watts against independently timestamped energy deltas during steady idle and load over several refreshes. On a multi-socket host, compare the sum of the socket readings. If comparing with MangoHud, record which sensor it selected so differences in measurement scope can be interpreted. Record the first hardware-confirmed model and result separately from fixture coverage.
